## Required Workflow

### Morning
1. Run `./scripts/daily-routine/start_day.sh` (canonical location after the Slice 0 rename — see [scripts/daily-routine/](scripts/daily-routine/)).
2. Review recent changelogs and merged PRs.
3. Check [Project #23](https://github.com/orgs/adc-quality/projects/23) for `Todo` / `In Progress` items.
4. Verify local stack is healthy: `python -m pytest -q` (Docker check arrives in Slice G).

### End of day
1. Run `./scripts/daily-routine/end_day.sh`.
2. Document technical decisions:
   - **During an active wave** (`/wave-execute` in progress or just completed): the wave summary at `docs/wave-execute/sprint-<N>-wave-<M>-<date>.md` is the canonical record. Daily changelogs are **optional** — the wave summary + PR descriptions already capture the work.
   - **Outside of a wave** (hotfixes, solo exploration, sprint-boundary work): write `changelogs/CHANGELOG_YYYY-MM-DD_<name>.md` as before.
3. Commit changelog (if written) as `docs: add changelog for YYYY-MM-DD`. Wave summary commits land in the PR they belong to, not separately.
4. Update GitHub issues / Project #23 status.

> **Artifact grain**: changelog = day-level technical notes. Wave summary = sprint-wave-level patterns, friction, and learnings (auto-generated by `/wave-execute` Phase 5, with a Human Verdict section the operator fills in). The wave summary is the bridge between daily detail and strategic plan — use it for retros and trend-spotting; use changelogs for "what did I touch today" when not in a wave.

### Sprint / Task Execution
1. **GitHub Issues** are the unit of work. Acceptance criteria, file references, story points required. Close on PR merge with summary.
2. **Context management**: run `/handoff` when approaching the context limit. The skill auto-pulls git state and conducts a short interview; output goes to `docs/handoffs/`. See `.claude/skills/handoff/SKILL.md`.
3. **Work incrementally**: complete one task, close the issue, then move to the next. Don't batch task completions.
4. **Proactive issue capture**: create GitHub issues for ALL recommendations and ideas you surface. Label discretionary work `could have`.

### Issue Hygiene
- **Naming**: conventional commit style — `feat(scope):`, `fix(scope):`, `chore(scope):`, `test(scope):`, `docs:`. **Never** `[brackets]`, `Task N:`, or `Sprint N:` prefixes.
- **Slice labels** (Sprint 1 onward): every issue gets one of `slice-0-baseline`, `slice-a-auth`, `slice-b-observability`, `slice-c-resilience`, `slice-c2-scheduled`, `slice-d-part1`, `slice-d-part2`, `slice-g-part1`, `slice-g-part2`, `slice-h-closure`. See [docs/CLEANUP_PLAN.md](docs/CLEANUP_PLAN.md) for the slice catalog.
- **Priority**: `P0` / `P1` / `P2` (Project #23 field).
- **Size**: `XS` / `S` / `M` / `L` / `XL` (Project #23 field).
- **Close-on-ship**: when a PR ships work satisfying an issue's ACs, close the issue immediately with a comment referencing the PR.
- **Guide-friction sync**: run `/guide-friction-sync` at slice close to mirror open `docs/guide-friction.md` entries to Project #55. See `.claude/skills/guide-friction-sync/SKILL.md`.

## Hard Rules

### Code and safety
- Follow existing patterns before introducing new ones — but the **architecture guide patterns** ([docs/CLEANUP_PLAN.md](docs/CLEANUP_PLAN.md) lists which slice introduces which) override ad-hoc local conventions.
- **Never hardcode credentials or secrets**: use `.env` + the tool-prefix convention. The PIN `"9420"` in [tools/system_locator/system_locator_app.py](tools/system_locator/system_locator_app.py) is a known violation tracked in Slice A.
- **Never store absolute filesystem paths in the database** — the [tools/print_requests/db.py](tools/print_requests/db.py) `uploaded_file_path` / `uploaded_image_path` columns currently violate this; tracked in Slice D-part1.
- **Never call `init_db()` / `_ensure_db()` at module import time** — use `init_app(app)` instead. Slice 0 enforces this; a CI test will fail anyone who re-introduces it.
- **Remove dead imports immediately when replacing a module attribute.** When a DB-layer refactor moves an attribute (e.g. `inventory_app.DB` → `inventory.db.DB_PATH`), delete the old `import ... as _old_module` line in the same commit. Dead imports that shadow replaced attributes cause `AttributeError` at runtime and produce merge conflicts when a parallel stream fixes the same file. Grep for the old name before committing (replace `_old_module` with the actual previous import alias, e.g. `_inventory_module`): `grep -r "_old_module" app.py tests/`.
- **Workspace hygiene**: do not create throwaway scripts in the repo root or `tools/` folders. Use `.scripts/` for ad-hoc tooling and clean up afterward.
- **Never use `innerHTML` to render server-sourced or user-supplied data** in templates or JavaScript. Use `textContent`, `createElement`, or DOM construction instead. This applies especially to async polling templates (Celery task status, JIRA import) — any dynamic error/status message inserted into the DOM is an XSS sink if set via `innerHTML`.

### 5-tool coverage discipline
Every infrastructure change must explicitly answer how it lands in each of the five tools:
- **Inventory** ([tools/inventory/](tools/inventory/))
- **RF Chamber** ([tools/rf_chamber/](tools/rf_chamber/))
- **Equipment Checkout** ([tools/checkout/](tools/checkout/))
- **System Locator** ([tools/system_locator/](tools/system_locator/))
- **3D Print Requests** ([tools/print_requests/](tools/print_requests/))

PR descriptions for infrastructure work **must include a 5-row coverage matrix** with status `Applied` / `Done` / `N/A-with-reason` per tool. Skipping a tool without explanation is a review-blocking defect.

### Git push and merge policy
- **Feature branches**: follow the architecture-guide naming. **Preferred** (concern-grouped, one per sprint): `feature/sprint-N-<concern>` with worktree `../lab-tech-portal-sprint-N-<concern>`. **Per-issue** (only for genuinely isolated work): `feature/issue-NNN-<short-desc>`. See [docs/workflows/multi-agent-worktree-workflow.md](docs/workflows/multi-agent-worktree-workflow.md) for the full convention and [docs/workflows/worktree-lessons-learned.md](docs/workflows/worktree-lessons-learned.md) for the "when to split vs group" decision tree.
- **PR titles MUST include the JIRA prefix**: `QENG-16846: <type>(<scope>): <summary>` (e.g., `QENG-16846: chore(slice-0): scaffolding for guide-based cleanup`).
- **Protected branches**: never force-push or push directly to `master`. Use PR workflow.
- **PR merge requirements**:
  1. All CI checks must pass (including the Jira-check workflow on branch `chore/add-jira-status-check-workflow` once merged).
  2. Automated PR review (Copilot or equivalent) completed; valid issues addressed via [tiered review](docs/workflows/pr-review-tiered.md) — round 1 broad, round 2 narrow, round 3+ defer.
  3. Human review optional for solo work (recommended for complex changes).
  4. Manual merge via GitHub UI only.

### Parallel-agent git workflow
- **Use git worktrees** for parallel work — **group by concern area, not per issue**. See [worktree lessons learned](docs/workflows/worktree-lessons-learned.md).
- Before creating worktrees, check file overlap. If >30% shared files between issues, group them.
- Naming: `../lab-tech-portal-sprint-N-<concern>` for sprint batches; `../lab-tech-portal-hotfix-NNN` for isolated hotfixes.
- Open worktrees in separate IDE windows. Cleanup with `git worktree remove <path>` after PR merge.
- **Prefer fewer, larger PRs** when issues share files. Fewer PRs = fewer rebase cycles, fewer duplicate review comments, fewer migration collisions.
- PRs must complete the checklist in `.github/pull_request_template.md` (added in Slice 0).

### Branch and merge hygiene
- Before creating a second branch, check file overlap against open PRs:
  ```bash
  comm -12 <(gh pr diff NNN --name-only | sort) <(git diff master --name-only | sort)
  ```
  If overlap > 30%, merge the first PR before starting the second.
- **Rebase against master daily**: `git fetch origin && git rebase origin/master` on active branches.
- **Push review fixes to the PR being reviewed**, never to a sibling branch.
- **Check migration numbering before branching** (Alembic, from Slice D-part2): never create a migration with a number already in-flight on another branch.
- Full sequence: [docs/workflows/merge-and-review-workflow.md](docs/workflows/merge-and-review-workflow.md)

### Centralization refactors

When replacing a literal X with `$CONFIG.foo` (or any equivalent shared-constant token), first group all callsites of X by the *logical entity* they reference — not by the textual value. Introduce one `$CONFIG.*` key per distinct entity, even when literals look identical or near-identical. Coincidentally-similar values pointing to different entities are the classic trap. Verify by running each newly-parameterized callsite mentally against the resolved value before committing.

**Worked example.** Project #23 (`PVT_kwDODlOvwc4BOhf-`) and Project #26 (`PVT_kwDODlOvwc4BPI7E`) share the same `PVT_kwDODlOv…` prefix — eyeballing them as "the same project ID" is the trap. They are distinct GitHub Projects with distinct Priority/Size/Status field IDs. The Sprint 6 Wave 2 centralization (PR #117) collapsed both onto `$CONFIG.github.project_id`, silently routing `defer-pr-comments` writes to the wrong board. See `docs/wave-execute/friction-inventory.md` entry **F12** for full root-cause.

**Markdown-link corollary.** Only command/query parameters consumed by skills should use `$CONFIG.*` — gh CLI flags, GraphQL inputs, file paths used as variables. Do not parameterize markdown link **text** or link **targets**: the read-then-resolve mechanism doesn't substitute at render time, so the placeholder would display literally to humans (and rendering can't follow a placeholder target).

## Architecture Patterns

This repo follows patterns from the **QE Application Architecture Guide** (Step 1.5):
https://github.com/adc-quality/qe-architecture-ai-assisted-guide

When adding new infrastructure (auth, rate limiting, real-time, observability, RBAC), **check the pattern library first**. Adopting a documented pattern beats reinventing one. Each adoption is tracked as a slice in [docs/CLEANUP_PLAN.md](docs/CLEANUP_PLAN.md).

**Patterns currently used in this repo:**
- **Slice A** — RBAC warn-only / enforce mode: `services/rbac.py` + `services/okta_auth.py` (groups claim). Pattern citation placeholder: `docs/patterns/auth/multi-mode-auth.md` (not yet written — see guide-friction F04).
- **Slice A** — CSRF + rate limiting: `CSRFProtect(app)` + `Limiter(app, ...)` registered in `app.py`; `{{ csrf_token() }}` injected in all 5-tool POST forms.
- **Slice A** — Centralized config fail-fast: `config.init_app(app)` in `app.py`; `validate_config` raises `ValueError` in production when `SECRET_KEY` is default.

**Code that adopts a pattern must cite it** with a header comment:
```python
# Pattern: docs/patterns/<category>/<name>.md (qe-architecture-ai-assisted-guide @ <SHA>)
```

When adopting a pattern, follow the canonical reference linked in the pattern doc and adapt to this repo's conventions (tool-specific env prefixes, blueprint structure, etc.).

**Guide-friction log:** any time a pattern doc is unclear, wrong, or missing context needed for this repo, append a note to [docs/guide-friction.md](docs/guide-friction.md). At end of slice, those notes become PRs back to the guide repos.
