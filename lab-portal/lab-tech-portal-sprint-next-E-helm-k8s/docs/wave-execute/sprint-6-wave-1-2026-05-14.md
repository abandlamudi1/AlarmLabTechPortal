## Friction encountered

### F09 (new) — `sh -c` Docker CMD without `exec` breaks SIGTERM forwarding

- **Pattern**: A Dockerfile CMD of the form `["sh", "-c", "celery -A celery_app.celery worker ..."]` causes the worker to run as a child of `sh`, not as PID 1. SIGTERM from `docker stop` / orchestrator goes to `sh`, which does not forward — graceful shutdown is silently broken; worker is SIGKILL'd after the timeout.
- **Root cause**: Standard ergonomic shell-form CMD for env-var expansion (`${CELERY_WORKER_CONCURRENCY:-2}`) does not prepend `exec`; the wrapping shell stays alive and absorbs signals.
- **Recurrence**: new (first observation). Caught by Copilot review of PR #111 (Stream E) Round 1. Classified BUG / MUST FIX. Fixed by prepending `exec ` inside the `sh -c` string.
- **Mitigation applied this wave**: inline fix in #111 commit `fb3317a` — `["sh", "-c", "exec celery -A celery_app.celery worker ..."]`.
- **Proposed action**: add to `AGENTS.md` hard rules as "When using `sh -c` for env-var-substituted CMD/ENTRYPOINT, prepend `exec` so the target process is PID 1 and receives signals." Or, better, prefer JSON-array CMD when env-var substitution isn't needed.

### F10 (new) — Raw exception message exposed to end-user form errors

- **Pattern**: `errors.append(str(exc))` where `exc` is a `requests.RequestException` (or similar) leaks request URL, TLS handshake detail, internal hostnames, and library internals to UI users.
- **Root cause**: Convenient `str(exc)` pattern for surfacing pre-flight failures; exception messages from external libraries are not user-facing copy.
- **Recurrence**: new (first observation). Caught by Copilot review of PR #113 (Stream G) Round 1. Classified SECURITY / MUST FIX. Fixed by raising `JiraServiceError("Could not reach Jira: <safe summary>")` and rendering only the safe-summary string.
- **Mitigation applied this wave**: inline fix in #113. The handler now formats a user-safe message and logs the raw exception server-side.
- **Proposed action**: candidate `AGENTS.md` hard rule — "Never pass `str(exc)` from an external-library exception directly to a user-facing form error or response body. Catch, log raw, render a sanitized summary."

### F11 (new) — Config field casing inconsistency within the same dataclass

- **Pattern**: New config fields were added as lowercase (`worker_prefetch_multiplier`, `result_expires`) while the existing fields in the same class are UPPERCASE (`CELERY_WORKER_CONCURRENCY`, `CELERY_QUEUES`). This passed tests but violates the file's own convention.
- **Root cause**: Dev agent took the field names verbatim from the Celery library's settings keys (which are lowercase) without checking the surrounding convention.
- **Recurrence**: new (first observation). Caught by Copilot review of PR #111 (Stream E) Round 1. Classified ROBUSTNESS.
- **Mitigation applied this wave**: inline fix in #111 — renamed to `WORKER_PREFETCH_MULTIPLIER`, `RESULT_EXPIRES`.
- **Proposed action**: add a one-line note to AGENTS.md or the per-tool README: "Match the casing of surrounding fields when adding to a config dataclass; do not import library-conventional casing as-is."
