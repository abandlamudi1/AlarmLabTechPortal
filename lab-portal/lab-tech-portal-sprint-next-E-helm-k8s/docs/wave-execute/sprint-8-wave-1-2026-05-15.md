## Friction encountered

### New: F16 — dev-only Python packages must be in the test Docker image, not just `requirements-dev.txt`

- **Pattern**: Three streams (A `pytest-cov`, C `moto`, D `fakeredis`) hit the same CI failure on first push: tests imported a dev-only package that was in `requirements-dev.txt` but NOT installed in the `lab-tech-portal:test` Docker stage. The Dockerfile's test stage only installs `pytest==9.0.2` explicitly; everything else in `requirements-dev.txt` is invisible to CI.
- **First observed**: Sprint 8 Wave 1 (2026-05-15) — caught by Copilot on PR #134 in advance, surfaced as a real CI failure on PRs #134, #137, and #139.
- **Root cause**: `Dockerfile`'s test stage uses `pip install --no-cache-dir pytest==9.0.2` rather than `pip install -r requirements-dev.txt`. Local devs run pytest in their venv with `requirements-dev.txt` installed, so the gap is invisible until CI runs.
- **Recurrence**: First observation, but observed in three parallel streams simultaneously — F-level.
- **Mitigation applied this wave**: each stream added its specific package to the Dockerfile test stage's `pip install` (Stream A added `pytest-cov`, Stream C added `'moto[s3]'`, Stream D added `fakeredis`). Inconsistent style — three streams independently making the same kind of change.
- **Proposed action**: Refactor the Dockerfile test stage to `COPY requirements-dev.txt . && pip install -r requirements-dev.txt` (or similar), so any future dev-dep addition is picked up automatically. Small follow-up issue, label `infrastructure` + `wave-friction`.

### New: F17 — UID mismatch when CI bind-mounts the workspace into a non-root test container

- **Pattern**: pytest-cov's data-file write to `/coverage/.coverage` failed with `DataError: unable to open database file` even though tests passed. The `appuser` (UID 1000) in the test container can't write to the GitHub Actions runner's workspace (UID 1001 ownership).
- **First observed**: Sprint 8 Wave 1, PR #134 second CI run.
- **Root cause**: Test Docker stage runs as `appuser` for production parity; CI bind-mounts the host workspace. Coverage data goes to the volume → host UID mismatch → write denied.
- **Recurrence**: First.
- **Mitigation applied this wave**: Stream A added `--user root` to the coverage-related `docker run` invocations. The test image is ephemeral and never shipped to production, so root execution is safe here.
- **Proposed action**: None for now (the fix is local to the coverage steps). If F16's "install from requirements-dev.txt" refactor lands, document the `--user root` requirement at the same time.

### New: F18 — Load-test framework breaks against production-default request guards

- **Pattern**: Locust HttpUser does not fetch CSRF tokens and shares one source IP across all simulated users. The portal's production defaults (`WTF_CSRF_ENABLED=true`, `RATELIMIT_DEFAULT=60 per minute` per-IP) silently invalidate ~30% of the write-mix tasks and ~98% of all requests after minute 2.
- **First observed**: Sprint 8 Wave 1, PR #136. Caught by Copilot in round 1.
- **Root cause**: The kickoff prompt told the agent to "auth-bypass via OKTA_ISSUER absence" but didn't mention CSRF or rate limiting — both also gate writes.
- **Mitigation applied this wave**: PR #136 added a `services.web` override block to `docker-compose.load.yml` that sets `WTF_CSRF_ENABLED=false` and `RATELIMIT_DEFAULT="100000 per minute"` only when the load-test overlay is layered. Production unaffected. README has a table documenting the deliberate deviation.
- **Proposed action**: When a future stream writes any load-test, integration-test, or chaos-test compose overlay, the kickoff prompt should include the standard "relax production-default request guards" checklist (auth bypass, CSRF, rate limiting, JIRA_DRY_RUN). Add to a prompt-checklist doc.

### New: F19 — Backward-compatibility shims that don't match the caller's path convention are worse than no shim

- **Pattern**: `S3CompatibleStorage.url_for()` initially had a backward-compat branch checking `os.path.exists(key)` to detect legacy filesystem paths and return them unchanged. The check resolves against the process CWD (not the upload root), so it was useless — legacy local files would not be detected and callers got presigned URLs for objects that didn't exist in S3.
- **First observed**: Sprint 8 Wave 1, PR #139, Copilot round 1.
- **Root cause**: The agent put backward-compat at the storage-layer abstraction. The storage layer doesn't know the calling routes' upload-root convention — so any path check there is guesswork.
- **Mitigation applied this wave**: removed the check from `url_for()` entirely. Backward-compat moved to the calling routes (`download_request_file`, `preview_request_file`, `inventory.qr`) which DO know the convention (they call `_resolve_upload_path(stored)` or `_qr_dir()/filename`). The storage method always returns a presigned URL now; the route serves the legacy file FIRST and only falls through to `url_for` when no legacy file exists.
- **Proposed action**: General rule for future abstractions: "Backward-compat shims belong at the layer that knows the legacy convention, not at the abstraction boundary." Note in AGENTS.md or the architecture guide.

### New: F20 — URL-shaped config values must be redacted by name pattern AND userinfo content

- **Pattern**: `SESSION_REDIS_URL` could embed managed-Redis credentials (`redis://user:password@host:6379/1`). The existing `SECRET_KEY_FIELD_PATTERN` regex matched only `*_KEY|*_SECRET|*_PASSWORD|*_PAT|*_TOKEN` field names — `SESSION_REDIS_URL` slipped through and the password would be logged verbatim by `render_config_summary()`.
- **First observed**: Sprint 8 Wave 1, PR #137, Copilot round 1.
- **Root cause**: Redaction was name-pattern-only. Any `*_URL` field that embeds userinfo (managed Redis, managed Postgres, S3 endpoints with embedded keys) bypasses the pattern.
- **Mitigation applied this wave**: PR #137 added a content-shape redactor — `_redact()` now also strips userinfo from any `*_URL` value where the URL contains a `@` in the userinfo segment. Same `_redact_url_userinfo()` helper added in app.py for the session-init logging path.
- **Proposed action**: Audit existing config keys for embedded-credential URL patterns — `CELERY_BROKER_URL`, `DATABASE_URL`, `S3_ENDPOINT_URL`, others. They're covered by the new redactor, but documenting the rule in AGENTS.md prevents the next contributor from reverting it as "redundant".
